\chapter{GPU Implementation and Validation}
\label{ch:gpu}

\section{Port architecture}
\label{sec:gpuport}

The null-geodesic core is ported to a GLSL compute shader (Vulkan,
double precision) using the same second-order Mino-time formulation
(\texttt{engine/shaders/geodesic.comp.glsl}), with all per-frame
parameters delivered through a bindless (update-after-bind) descriptor
table — one global resource array, written once, indexed by the shader,
so no per-frame descriptor churn ever appears on the timeline.

\subsection{Double-precision trigonometry on the GPU}

GLSL exposes \texttt{double} arithmetic (\texttt{shaderFloat64}) but
\emph{no} double-precision transcendentals, and the Carter equations
need $\sin\theta, \cos\theta$ at full precision every step. The shader
implements them by quadrant-tracking argument reduction to
$|x| \le \pi/4$ followed by fixed truncated Taylor polynomials — degree
11 for sine, degree 10 for cosine (\texttt{dsin\_core},
\texttt{dcos\_core}). (The companion journal paper called the pair
``minimax''; the coefficients are in fact the Taylor ones, and this
report documents the code as written. A Remez pair of the same degree
would gain roughly one decimal digit at the interval ends — immaterial
below the validation threshold, as the measurement shows.)
Fig.~\ref{fig:trigerr} evaluates the shader's exact polynomial
arithmetic against library $\sin/\cos$ across the reduction interval:
the truncation error rises to $\sim 7\times10^{-12}$ for sine
($\sim 5\times10^{-11}$ for cosine) at $|x| = \pi/4$, comfortably below
the per-step tolerances of the fp64 metrology path and five orders
below the 0.01 pixel-diff acceptance gate.

How those per-step errors accumulate over a ray is worth budgeting
explicitly. The trig truncation acts as a small perturbation injected
each step with effectively random sign as $\theta$ sweeps its
oscillation; over a worst-case ray of $\sim$1200 steps the random-walk
accumulation is $\sqrt{1200}\times7\times10^{-12} \approx
2\times10^{-10}$ — utterly negligible against every tolerance in the
pipeline \emph{except} exactly at the capture/escape separatrix, where
Chapter~\ref{ch:shadow}'s exponential divergence amplifies any
perturbation without bound. That budget predicts precisely the
validation outcome observed below: bit-level agreement everywhere
except isolated flips on the one-pixel critical circle.

The precision asymmetry of consumer GPUs is the structural fact behind
the whole port design. Gaming-class silicon executes double-precision
arithmetic at a small fraction of single-precision throughput (1:32 on
the Pascal generation of the test GPU), because fp64 units are a
die-area luxury reserved for compute cards. The project therefore
splits cleanly: the \emph{metrology} path runs fp64 offscreen, unpaced
by any display, where a slow-but-exact frame is acceptable; the
\emph{interactive} path runs fp32 at speed with a shortened optical
path (Section~\ref{sec:watchdog}) so that accumulated fp32 drift stays
below visual perceptibility. No quantitative number in this report
ever originates from the fp32 path — the split is enforced by
pipeline, not by discipline.

\section{Validation against the CPU reference}
\label{sec:gpuvalidation}

A $64\times64$ shadow rendering is
compared pixel-by-pixel against the CPU reference
(\texttt{validation/compare\_shadow.cpp}): the mean absolute
difference is \GpuMeanDiff{} (gate threshold 0.01), with \GpuOutliers{}
pixels differing by more than 0.1 — every one of them on the
one-pixel-wide critical boundary, where capture/escape classification
is legitimately ambiguous at pixel resolution (the boundary rays of
Chapter~\ref{ch:shadow} diverge exponentially, so the last representable
bit decides the pixel). The maximum single-pixel difference is
\GpuMaxDiff{}, i.e.\ one full classification flip on the critical
circle; away from that circle the two implementations agree to
round-off. This is the strongest statement available for a
cross-architecture port: identical mathematics, independent compilers
and schedulers, indistinguishable physics.

\section{Watchdog-safe dispatch and the precision split}
\label{sec:watchdog}

Two practical constraints shaped the port. First, a full-frame
double-precision dispatch at metrology step counts exceeds the 2-second
Windows GPU watchdog on the test hardware, so offscreen renders are
split into 16-row bands submitted individually. Second, the interactive
path (Chapter~\ref{ch:instrument}) runs the same equations in single
precision from a nearby camera ($r_{\rm cam} = 60\,M$), where the
shortened optical path keeps single-precision drift visually negligible;
all quantitative results in this report come from the double-precision or
CPU paths. All configurations run with zero Vulkan validation-layer
errors.

\section{Performance}
\label{sec:performance}

The CPU baseline integrates \BenchCpuNullStepsPerS{} adaptive null-geodesic
steps per second per core (\BenchCpuTimelikeStepsPerS{} timelike;
\BenchCpuChristoffelPerS{} complex-step Christoffel evaluations). The
double-precision GPU port traces the validated $64\times64$ shadow tile
within the Windows watchdog budget in row-banded dispatches, and the
single-precision interactive path sustains
\BenchGpuFpsHd~fps at $1280\times720$
(\BenchGpuFpsFullhd~fps at $1920\times1080$;
$\approx$\BenchGpuMegaraysPerSHd{} million ray--geodesics per second) on a
GeForce GTX~1050 --- a 2016 notebook-class GPU --- with zero
validation-layer errors. (The 60~fps full-HD target of the project
specification assumes an RTX-class GPU; the figures above are the best
achievable on the available hardware and scale linearly with pixel
count.) Fig.~\ref{fig:bench} collects the benchmark artefacts: the CPU
per-core throughputs that set the offline render times, and the GPU
frame rate against pixel count, which follows the $1/N_{\rm px}$ line
closely — the workload is one geodesic per pixel with no shared state,
the embarrassingly parallel ideal, so the live renderer's
auto-resolution controller (Chapter~\ref{ch:instrument}) can trade
resolution for frame rate predictably.
